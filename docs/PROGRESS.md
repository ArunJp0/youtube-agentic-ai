## Known Limitations

- Semantic relevance now depends on the quality of the LLM's contextual understanding (when the planner succeeds) or on deterministic keyword/concept mapping (when it falls back) combined with what stock footage Pexels actually has for a given query. The deterministic fallback path still has no contextual understanding of ambiguous wording - it exists only as a safe, previously-validated degradation path, not a semantic solution in its own right.
- Visual QC inspects actual frame content (not just text metadata) and now runs inside the main pipeline, but it samples a small, fixed number of representative frames rather than every frame - a clip that changes content between sampled frames could still be judged on an unrepresentative moment.
- A QC-driven replacement re-evaluation is an additional vision call per attempt (bounded by `max_replacement_attempts`, not free).
- Repetition checking remains asset-ID/position based only, not frame-level computer-vision duplicate detection - controlled visual reuse may still occur.
- Perfect semantic stock-footage matching is not guaranteed: Pexels' inventory for a given query is finite, so even with duration-aware planning, semantic filtering, and vision QC, an occasional visual can still be only loosely related to its section - real review found this acceptable (~80-90% relevance) for the current MVP, not eliminated.
- For long videos where Pexels lacks enough unique matching stock footage, controlled asset reuse (and, as a last resort, looping) remains an accepted fallback rather than a hard failure.
- The main pipeline currently produces **two** MP4 outputs per run (the original assembled MP4 and a separate captioned MP4) rather than one final file - intentional for now; a future storage/cleanup milestone may remove the intermediate uncaptioned MP4 once captioning/upload has succeeded.
- Occasional very short, single-word caption segments can occur, driven by Whisper's own segment boundaries rather than `caption_segmentation.py`'s (split-only, never-merge) logic - manual review of the real integrated run found current readability acceptable, so no further caption segmentation tuning is planned unless a real problem is found.
- Stock footage semantic relevance remains good-enough-but-not-perfect and can vary run-to-run with live Pexels results - the visual pipeline (planning → selection → QC → assembly) is considered frozen for the current MVP and will not be further tuned unless a recurring, severe relevance problem appears.
- The BGM catalog is a manually curated local library (`assets/bgm/`) - there is no automatic licensed-music-provider integration yet. Populating it is a manual, one-time-per-track MVP step; the final production goal remains zero human intervention, with automated/licensed catalog sourcing deferred to a later milestone.
- Gemini mood planning is a single optional call per video; real validation showed it can be unavailable under Gemini free-tier rate limiting (429/503/timeouts), in which case the deterministic fallback `MusicPlan` (neutral/calm, low energy, ambient/cinematic, neutral/subtle required) is used automatically - mood selection is correspondingly generic whenever the LLM call doesn't succeed.
- The main pipeline now produces **three** MP4-related outputs per run on disk (the original assembled MP4, the captioned MP4, and the final BGM-mixed MP4), plus the `.srt` file, rather than a single final output - intentional for now as development/debug fallbacks; a future storage/cleanup milestone may remove the intermediate files once the final mixed MP4 has been used/uploaded successfully.
- Metadata content quality (title/description/tags/hashtags accuracy) depends entirely on the quality and accuracy of the input `ScriptResult`/narration - the Metadata Agent does not independently fact-check; an accuracy issue already present in upstream narration will pass through into the generated metadata (observed in both the standalone milestone and the real integrated run - see the Matthew Walker note above).
- The Metadata Agent's main-pipeline JSON artifact output (`output/metadata/<video-slug>.json`) is now read by the standalone YouTube Upload Agent's artifact discovery (`src/services/upload_artifact_discovery.py`), but only via a best-effort topic-matched lookup (no exact on-disk run-id link exists for metadata, unlike provenance/compliance) - a pre-existing gap, not introduced by the Upload Agent milestone.
- Thumbnail image selection has no true subject-detection - `composition` only controls which side of the frame hosts the text panel (with a translucent scrim guaranteeing contrast there), not literal awareness of where a photo's actual subject is; this is an accepted MVP simplification, not a bug.
- The current thumbnail style is a straightforward stock-photo-plus-text-overlay composite; more custom/cinematic thumbnail styles (e.g. via an AI image-generation provider) are a possible future V2 enhancement, not needed for the current MVP.
- The generated thumbnail file (`output/thumbnails/<slug>.jpg`) is now produced by every real pipeline run and is applied by the standalone YouTube Upload Agent via `videos.thumbnails.set` when an exact provenance-manifest-linked thumbnail is found for the run being published.
- Full provenance-aware compliance review depends on a persisted `ProvenanceManifest` existing for the run being checked; runs from before this milestone (or any run whose manifest write failed) are legacy artifacts with no manifest, and correctly resolve to `REVIEW` rather than a fabricated `PASS` - an honest limitation of the current MVP, not a defect.
- The semantic compliance review is a single advisory LLM pass, not independent fact-checking - it can only ever push toward `REVIEW`, never `BLOCK`, and a well-worded but still-misleading claim could pass through undetected, exactly like the equivalent limitation already noted for the Thumbnail Agent's hook-quality guard.
- Compliance is the pipeline's final gate for its own `completed`/`review_required`/`blocked`/`published`/`publishing_failed` status, and the `publishing` node enforces the exact same PASS gate (`publish_decision == "PASS"` checked directly on the typed field) as the standalone Upload Agent, since both reuse the identical `YouTubeUploadAgent` unchanged.
- Publishing through the main pipeline is opt-in, not automatic: a normal `run_pipeline`/`pipeline_demo.py` call still never uploads anything, even on a genuine PASS, unless a caller explicitly constructs a non-`"disabled"` `PublishingIntent` and a `YouTubeClient` and passes both in - this is a deliberate safety default, not an unfinished feature. `src/pipeline_demo.py`'s own CLI does not currently expose flags for this (it was intentionally left untouched by the integration milestone); a caller must use `run_pipeline`/`build_pipeline_graph` directly to enable publishing today.
- Real scheduling itself (an actual future `publishAt` accepted by the real YouTube API, through either the standalone CLI or the pipeline integration) has been validated only via dry-run preview, mocked integration tests, and channel/token-reuse checks - no real scheduled upload has been performed yet in this project. The real integrated validation performed was PRIVATE-only, per this milestone's explicit scope.
- **Accepted MVP validation limitation (not a known defect)**: the Compliance Remediation loop (bounded REVIEW → script correction → re-evaluation, in `src/workflows/pipeline_graph.py`) is comprehensively covered by 43 dedicated mocked tests and was real-validated for the surrounding machinery (compliance persistence, the video_slug collision fix, and the non-remediation PASS path, all confirmed against real providers), but the real live-provider REVIEW → `script_revision` → re-evaluation branch itself has not yet occurred naturally, since the one real validation run reached PASS immediately. This is intentionally not being forced by repeated real pipeline runs (an explicit MVP decision - see `docs/DECISIONS.md`); a naturally-occurring real REVIEW during future normal operation will provide that live-path validation.
- LangGraph's compiled pipeline graph has a single fixed entry point (`research`) - there is no way to resume/re-enter a compiled graph mid-way (e.g. directly at `publishing`) without either re-running every upstream stage or adding checkpoint/resume infrastructure, which does not exist yet. This is why the real integrated publishing validation reused the exact production publishing call path directly against an existing real PASS run rather than re-running the full pipeline. Checkpoint/resume support is accepted as optional future infrastructure (useful for crash-recovery and for resuming publishing against an older completed run without regeneration) - not required for the current MVP and not a blocker for any milestone closed so far.
- The Topic Planner's sensitivity-story keyword heuristic (`src/services/topic_sensitivity.py`) is intentionally lightweight and English-oriented, not a fact-checker or a second Compliance Agent - some lexical variations (e.g. plural forms) may not match a listed keyword, and a non-English deployment would need an equivalent keyword set for its own configured `TOPIC_LANGUAGE`. Accepted as future hardening, not a blocker.
- `src/topic_planner_demo.py` and `src/pipeline_demo.py` remain separate manual CLIs, and `src/workflows/pipeline_graph.py` itself still has no Topic Planner node - but a human is no longer required to bridge them: the new `AutonomousRunController` (see Autonomous Orchestration below) calls `TopicPlannerAgent.plan_topic()` and then `run_pipeline(...)` directly, in one coordinated run, with no manual copy/paste hand-off needed.
- Real validation of Topic Planner originally exercised `TOPIC_MODE=trending` (current news) only; **updated by the Current/Trending Topic → Research → Script Compatibility milestone**: `TOPIC_MODE=mixed` with `TOPIC_PLANNER_SOURCE=youtube` has now been real-validated end to end (15 real candidates considered, a real current-news candidate naturally selected and carried through Research/Script). The real `YouTubeTopicSourceProvider`/evergreen component of that composite source still has not been exercised against a real, working `YOUTUBE_API_KEY` in the same run (see the still-open item directly below) - it continues to degrade gracefully in its absence, which is what real mixed-mode validation actually observed.
- Real evergreen candidates in `TOPIC_MODE=mixed` still require a `YOUTUBE_API_KEY` (not currently configured) - the evergreen/YouTube component of the composite source fails gracefully in isolation without one, so mixed mode currently surfaces real current-news candidates only in practice; this is a known, accepted gap, not a defect.
- **Resolved in the Current/Trending Topic → Research → Script Compatibility milestone**: `WikipediaSearchProvider`'s naive keyword search on a full question-phrased topic string can still match tangentially/wrongly for a current-news topic (Wikipedia genuinely has no dedicated article for a brand-new event) - but Wikipedia is no longer the only research path for a current/trending topic. `ResearchAgent` now routes a `topic_source="current_news"` topic to the new `CurrentNewsSearchProvider` first, falling back to Wikipedia only as a bounded second attempt; for a purely evergreen topic, Wikipedia's own search-relevance characteristics are unchanged and remain a general, accepted limitation of keyword search over a full-question string.
- **Resolved in the Current/Trending Topic → Research → Script Compatibility milestone**: `ResearchAgent._extract_key_points`'s `_parse_bullet_points` no longer counts a leading, unmarked, colon-terminated LLM preamble line (e.g. "Based on the provided source material, here are 5 key points:") as a fabricated key point - fixed narrowly (only the very first non-blank line is ever eligible, and only when it has no bullet/number marker of its own), with a dedicated regression test covering the exact real Gemini pattern previously observed.
- The AI Video Generation architecture (`AIVideoProvider`, `LocalAIVideoProvider`, `MockAIVideoProvider`, the `VisualMediaService` integration seam) is fully implemented, tested, and preserved, but has only been real-validated once, standalone, via a demo-specific orchestration script (`src/ai_video_demo.py`) - not yet through the actual integrated `VisualMediaService`/`run_pipeline` path with a real `AIVideoProvider` configured end to end. A real paid provider (fal.ai/Kling, Seedance, Veo, PixVerse's official API) has not been integrated or budgeted for yet; `AI_VIDEO_ENABLED=false` remains the default, so Pexels stays the unconditional normal production path until a real provider is chosen and approved.
- The one real PixVerse-derived demo video (`output/ai_video_demo/why-do-cats-purr/final_ai_demo.mp4`) is explicitly NOT production-approved and will not be sent to the client - it exists only to prove the AI-video architecture can carry genuine AI-generated footage through the real TTS/captions/BGM/FFmpeg components end to end. All generated demo media stays under the existing Git-ignored `output/` tree - nothing from this experiment is (or should be) committed.
- `CurrentNewsSearchProvider`'s up-to-5 returned results for a given current-news topic are not guaranteed uniformly same-day - Google News legitimately mixes the fresh triggering story with older background coverage of the same ongoing situation (confirmed directly in real validation: one run's sources spanned 2026-04-03 to 2026-09-15). This is treated as acceptable, not a defect: roughly the recent 3-7 day window is considered genuinely "current," and older reliable sources remain useful as background/context, mirroring Wikipedia's own role on the evergreen path - not a same-day-only requirement.
- **Superseded by the Research Agent Production-Hardening milestone**: `ResearchAgent`'s substance gate is no longer "multi-provider path only" or purely a word-count check - it now runs uniformly on every provider (including plain evergreen), and a verbose-but-topically-irrelevant result is caught upstream by DIRECT/SUPPORTING/UNRELATED classification before substance is ever measured, so it can no longer inflate sufficiency. The substance measurement itself (`assess_substance`) remains a deterministic distinct-word-count check - it still is not, and is not meant to be, a standalone relevance classifier.
- `src/pipeline_demo.py` (the manual single-topic CLI, not driven by `TopicPlannerAgent`) remains unwired to `topic_source`, since a manually-typed topic has no Topic Planner classification to pass through - Research for that CLI still uses the default (Wikipedia-only) path, now itself subject to the full quality contract like every other path.
- **`ResearchAgent.research_focused_claim()`** - the bounded, single-claim research refresh Compliance Remediation uses to correct one already-flagged script section - does not go through the universal provider-independent quality contract described above; it remains a narrow, separately-scoped path with its own existing NO_EVIDENCE safety net (the LLM declines rather than fabricates when the source material doesn't address the claim). This is not part of normal initial Topic → Research → Script generation and was left unchanged by the Research Agent Production-Hardening milestone, consistent with not modifying Compliance Remediation's own behavior.
- **Topic Continuity's TIER 2 (evergreen fallback) and TIER 3 (qualified reserve) paths have mocked/automated coverage only, no real-provider validation yet** - the one real minimal validation performed naturally succeeded on TIER 1's first candidate, so TIER 2/TIER 3 were never reached live (deliberately not forced, to avoid unnecessary real API/LLM usage). This mirrors the same accepted-opportunistic-validation policy already used for Compliance Remediation's live REVIEW branch; a future real run that naturally exhausts TIER 1 will provide that live-path confirmation.
- The TIER 3 qualified reserve (`output/topic_reserve/`) starts empty in production until TIER 2 has run at least once and opportunistically seeded it (`TOPIC_CONTINUITY_RESERVE_SEED_ATTEMPTS`) - it is not pre-populated, by design (no video is ever pre-generated merely to satisfy this mechanism).
